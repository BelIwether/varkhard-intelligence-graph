# VARKHARD Intelligence Graph

VARKHARD Intelligence Graph traces AI agent access and explains security findings with evidence from an embedded Relate graph. Investigators can locate the earliest supported record, inspect the triggering action or permission, and follow the recorded path to the observed outcome.

## Use case

Security reviewers can see which agent acted on a resource, which permissions applied, and which interactions are linked in the graph. The dashboard reads a synthetic snapshot with five fictional agents and four fictional resources, including an external outbox represented by a graph node. The embedded snapshot shows recorded activity and rules evaluated against that data.

## Phase 1A support boundary

Phase 1A is a development and testing dashboard for one trusted operator on a local machine. Use synthetic or non-customer test data under your control. The dashboard API serves graph records without authentication. Keep FastAPI and Vite bound to `127.0.0.1`, with port forwarding, public tunnels, and external proxy routes disabled. Production and multi-tenant deployments are outside this support boundary.

## Run the dashboard

From the repository root, use Python 3.10 or later and Node.js 20.19+ on the 20.x line or 22.12+. The Graph demo runs locally without a database server or credentials.

### Linux and macOS

```sh

source .venv/bin/activate
python -m pip install -e '.[test]'
npm ci --prefix frontend
npm run build --prefix frontend
python -m uvicorn varkhard.api:app --host 127.0.0.1 --port 8010
```

### Windows PowerShell

Run the following from the repository root. The commands use the virtual environment's Python directly and work with Python 3.12 x64.

```powershell
py -3.12 -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -e ".[test]"
npm.cmd ci --prefix frontend
npm.cmd run build --prefix frontend
```

FastAPI serves the built React application and reads the bundled `examples/synthetic-demo.rl` snapshot. [Dashboard](http://127.0.0.1:8010/) · [API documentation](http://127.0.0.1:8010/docs)

For custom testing, use a trusted local VARKHARD Relate Single File generated by `GraphStore`. To create one with the synthetic fixtures, run `python -m varkhard --db data/phase1a-test.rl seed` with the virtual environment's Python, then set `VARKHARD_DB_PATH=data/phase1a-test.rl` in your shell before starting Uvicorn. In PowerShell, use `$env:VARKHARD_DB_PATH = 'data\phase1a-test.rl'`. The dashboard opens this file read-only.

For frontend development, keep the API running on port `8010` and run `npm run dev --prefix frontend -- --host 127.0.0.1` in another terminal. On Windows, use `npm.cmd` in place of `npm`. Vite proxies `/api` to FastAPI. Set `VARKHARD_API_URL` for the Vite process if you use a different loopback port. [Vite dev server](http://127.0.0.1:5173/)

## Dashboard walkthrough

1. Open **Intelligence Graph** from the top navigation. Drag the canvas to pan, use the zoom buttons to change scale, and drag individual nodes to reposition them. **Fit graph** fits the full graph to the canvas.
2. Select **Preview Agent** from the agent picker or the graph. The Inspector shows its grants, baseline permissions, and recorded actions, including the denied catalog write. Resource, permission, and interaction nodes have their own record and relationship details.
3. Open **Findings** from the navigation or the **Security findings** count. Select **Unauthorized Access**, **Excessive Permission**, or **Suspicious Chain**. The graph highlights available evidence and the Inspector shows the detector explanation, origin, trigger, involved entities, and recorded outcomes where available.

### Investigate a finding

| Control | What it does |
| --- | --- |
| **Trace Origin** | Focuses the earliest supported interaction or the relevant permission mismatch. |
| **Highlight Full Path** | Highlights all available nodes and links in the finding's trace. |
| **Show Affected Nodes** | Focuses directly involved records and their supported relationships. |
| **Step Through Evidence** | Highlights evidence one step at a time. Use the step controls or select an entry in the Inspector's timeline or policy comparison. |
| **Expand Investigation** | Gives the graph the workspace beneath the top navigation. Show or hide the Inspector as needed. Press **Escape** or select **Exit Focus Mode** to return to the dashboard with the current investigation and graph position. |
| **Reset Graph** | Clears the investigation selection and restores the default viewport and layout. |

For the demo Suspicious Chain, start at the Research Agent's read and follow the recorded handoff to the Relay Agent and its export to the simulated external outbox. The Inspector shows the timestamps, outcomes, and 180-second span within the rule's 600-second observation window.

### Search graph records

Type into **Search graph records** and use **Search category** to narrow results to AI agents, resources, actions, finding types, or interactions. Search by an agent or resource name or ID, an action, a finding category or rule ID, or an interaction ID. Select a result to focus the corresponding graph record or finding. Press **Enter** to select the first result, or **Escape** to dismiss results.

## Phase 1B local Knowledge workflow

Knowledge records a verified synthetic incident, derives a versioned advisory about the observed pattern, and tracks its review in local SQLite. The server recognizes the bundled synthetic snapshot by its pinned SHA-256 digest and validates the finding against that snapshot through a read-only Relate connection. `VARKHARD_DB_PATH` selects the Graph dashboard's snapshot. Knowledge uses the pinned bundle for its candidate evidence.

The existing Graph demo remains unauthenticated. The `/api/knowledge` routes require a configured, authenticated identity and use its server-assigned tenant and role for every request. Phase 1B shares the trusted local and loopback-only support boundary. Use the bundled synthetic data and keep the SQLite database and identities file under the local account's control. Filesystem permissions govern direct access to these files.

### Set up Knowledge on Windows

Complete the PowerShell installation and frontend build above. In a private PowerShell terminal at the repository root, generate one analyst and one reviewer in the same demo tenant. The script refuses to overwrite an existing identity file. It saves token hashes to a Git-ignored file and captures the tokens in this shell's variables.

```powershell
$env:VARKHARD_LOCAL_IDENTITIES = 'data/local-knowledge-identities.json'
$initializeIdentities = @'
import hashlib
import json
import os
import secrets
from pathlib import Path

path = Path(os.environ["VARKHARD_LOCAL_IDENTITIES"])
path.parent.mkdir(parents=True, exist_ok=True)
roles = ("analyst", "reviewer")
tokens = [secrets.token_urlsafe(32) for role in roles]
records = [
    {
        "actor_id": f"demo-{role}",
        "tenant_id": "demo-team",
        "role": role,
        "token_sha256": hashlib.sha256(token.encode("ascii")).hexdigest(),
    }
    for role, token in zip(roles, tokens)
]
with path.open("x", encoding="utf-8") as file:
    json.dump(records, file, indent=2)
for token in tokens:
    print(token)
'@
$analystToken, $reviewerToken = $initializeIdentities | & .\.venv\Scripts\python.exe -
if ($LASTEXITCODE -ne 0) { throw 'Local identities setup failed.' }
```

Keep this terminal for the two tokens. Start FastAPI in a second PowerShell terminal at the repository root with the two Phase 1B paths set. Stop any earlier FastAPI process on port `8010` first.

```powershell
$env:VARKHARD_KNOWLEDGE_DB = 'data/knowledge.sqlite3'
$env:VARKHARD_LOCAL_IDENTITIES = 'data/local-knowledge-identities.json'
& .\.venv\Scripts\python.exe -m uvicorn varkhard.api:app --host 127.0.0.1 --port 8010 --no-access-log
```

On Linux and macOS, export the same variables and start the loopback server with `--no-access-log`. The identity file is a JSON array whose entries contain `actor_id`, `tenant_id`, `role` (`analyst` or `reviewer`), and the hexadecimal SHA-256 `token_sha256` of an independently generated `secrets.token_urlsafe(32)` token. Keep plaintext tokens in shell variables or enter them directly into the Knowledge sign-in field.

### Register and review the demo incident

1. Open **Knowledge** in the dashboard. In the private setup terminal, enter `$analystToken` to display its value. Paste that value into **Knowledge access token** and select **Connect**. Choose the verified **Suspicious Chain** candidate to register the incident, then create its advisory draft.
2. Check the draft's evidence classification, claim limits, and version digest. Submit the version for review.
3. Select **Disconnect**, then connect with `$reviewerToken` from the same demo tenant. Review the submitted version and approve or reject it. The server requires the reviewer to be a different actor from the author.
4. Reconnect as the analyst to start a new draft from the latest approved or rejected version. Earlier versions and their review decisions remain in the advisory history.

The browser holds the bearer token in memory for the active page. Reloading requires entering a token again. A review decision applies to the local advisory version. Establishing intent, impact, or effectiveness requires separate evidence.

An advisory has a minimized envelope with its knowledge ID and version, schema and pattern versions, evidence classification, claim limits, and a validation-suite identifier. Private incident references and accounting fields are outside that envelope. The digest is lowercase SHA-256 over sorted, compact UTF-8 JSON of the envelope with the digest field excluded. The validation-suite identifier is recorded for future evaluation. The workflow ends at local review and stores version transitions and audit events in SQLite. The application audit is append-only. Its integrity depends on control of the host files.

## Dashboard API

| Route | Response |
| --- | --- |
| `GET /api/graph` | Agents, resources, permissions, interactions, graph nodes and edges, findings, and snapshot metadata. |
| `GET /api/agents` | AI agent records. |
| `GET /api/resources` | Resource records with classification and boundary. |
| `GET /api/findings` | Findings with rule explanations, evidence, graph highlight IDs, and structured investigations. |

Each API request opens its own read-only connection, queries the file, and closes the connection on the same worker thread. The API includes `Cache-Control: no-store` on responses, including errors.

A locked, unavailable, or unsupported snapshot returns HTTP `503`. Close any active writer, check the configured path, or select a supported VARKHARD snapshot before retrying. A snapshot created by `GraphStore` with zero records returns an empty graph.

The graph response's `source` includes the basename of the resolved snapshot opened for that request, its read-only status, and `synthetic_demo`, which identifies the bundled sample file. When the configured path is a symlink, the response describes the target used for the request.

`GET /api/graph` reports `evidence_quality.status` as `complete` or `incomplete`, with counts of rejected records (`invalid_records`) and rejected or missing relationships (`invalid_relationships`). A rejected record and its links can contribute to both counts. The dashboard warns when evidence is incomplete. If a policy scope is incomplete, the response omits findings in that scope that depend on the absence of a grant or baseline. Other supported findings remain available.

Findings from `GET /api/graph` and `GET /api/findings` include an additive `investigation` object. Existing finding fields are also available.

| `investigation` field | Meaning |
| --- | --- |
| `origin` | Earliest supported event or policy mismatch as an evidence step, or `null`. |
| `trigger` | The finding's associated action or grant as an evidence step, or `null`. |
| `steps` | Evidence steps in their documented order. A policy comparison may include a grant and baseline records. |
| `affected_node_ids` | Graph IDs for records directly involved in the finding. |
| `node_ids`, `edge_ids` | Verified graph references included in the investigation trace. |
| `complete` | Whether the records and links cover the expected evidence for the rule. Establishing cause requires additional evidence. |

Each step has a `title`, `description`, `node_ids`, and `edge_ids`. Its `record_node_id` points to the primary graph record. `occurred_at` is a Unix timestamp in seconds when an event is recorded. `action` and `outcome` reflect the record when available, with outcomes of `success` or `denied` for interactions.

## Findings

Every finding includes a rule ID, an explanation, and evidence from the graph. Timestamps in the evidence use ISO 8601 UTC. The seeded demo produces one finding for each rule.

| Rule | What it checks | Demo evidence |
| --- | --- | --- |
| `unauthorized_access` | An observed interaction has no current grant matching its agent, resource, and action. A denied event records an attempt. | `interaction-catalog-write-denied` records a write attempt from the Preview Agent, whose grant covers reading the catalog. |
| `excessive_permission` | A grant has no matching entry in the approved least-privilege baseline. An unused grant can be valid when the baseline approves it. | `grant-archive-delete` allows the Maintenance Agent to delete from an archive whose baseline allows only read and write. |
| `suspicious_chain` | Linked successful interactions show an agent reading a restricted resource, handing it off to another agent, and that recipient exporting to an external resource. The three event timestamps must strictly increase and span at most 600 seconds. | `interaction-ledger-read` → `interaction-ledger-handoff` → `interaction-outbox-export`. The related actions occur within 180 seconds and are individually granted. |

### Interpret the evidence

- The investigation's origin identifies the first relevant record supported by the trace. The Inspector shows **Root cause not established** when the snapshot supports only an observed origin or policy mismatch.
- Trace construction validates graph references and uses explicit event links and timestamps to order recorded activity. Missing or inconsistent references can produce a partial trace with fewer supported steps.
- A stored `TRIGGERS` link between two validated events in the same UTC second remains visible in the graph as a recorded link with unknown order. Ordered investigations and Suspicious Chain detection require strictly increasing timestamps. Self-links and links that contradict recorded timestamps are rejected.
- A handoff's declared recipient is unverified unless a matching `HANDED_TO` relationship is validated. An unverified declaration cannot add an affected entity or an incoming action. A denied handoff records an attempt, even when its intended destination is verified.
- For Unauthorized Access, the flagged interaction is the trigger. The trace can follow up to 64 recorded events backward when `parent_id`, the `TRIGGERS` edge, and timestamps agree. The rule checks grants currently stored in the file. Evaluating historical policy requires permission history. A `denied` outcome records an attempt.
- For Excessive Permission, the grant mismatch is both origin and trigger. The related least-privilege entries are policy evidence. Interpreting the mismatch depends on baseline coverage. The grant finding may have no associated interaction or outcome.
- For Suspicious Chain, the detected read is the origin, and the external export completes the rule pattern. The path follows the recorded read, handoff, and export. Establishing intent or effects outside the graph requires separate evidence.
- The bundled snapshot is synthetic. Investigations run against the selected read-only Relate file and report the relationships, permissions, and events recorded there.

## How it uses Relate

The Python core uses embedded Relate Single File via `relate-db==1.2.0`. Single File lets independent CLI processes share a persistent graph through one portable file. The default path is `data/varkhard-graph.rl`. Parameterized Cypher writes graph records and reads permission scopes, event targets, and explicit handoff paths.

```text
(AIAgent)-[:HAS_PERMISSION]->(Permission)-[:ON_RESOURCE]->(Resource)
(AIAgent)-[:PERFORMED]->(Interaction)-[:TARGETS]->(Resource)
(Interaction)-[:HANDED_TO]->(AIAgent)
(Interaction)-[:TRIGGERS]->(Interaction)
```

Grant and baseline records are both `Permission` nodes, each tagged with its kind. The two interaction relationships represent the recipient of a handoff and explicit links from parent events to child events. The interaction model stores `occurred_at` as Unix seconds. Detection traverses these relationships to find the agent, resource scope, and ordered chain behind each explanation.

Relate locks the Single File while a writer has it open. Wait for the writer to close before opening the same file for analysis. Analysis uses `read_only=True` on an existing file. Multiple read-only connections can coexist, and a writer can reopen the file once the readers close. Each ingest commits a batch and calls `flush()` to checkpoint the committed data. When embedding `GraphStore` in Python, open it, perform queries or writes, and close it on the same thread. Use its context manager to release the connection promptly.

The automated tests use temporary Relate files and exercise persistence after closing and reopening the database. See the [Relate Python API reference](https://relatedb.ai/docs/reference/api/python/).

| `tests/` | Storage, detection, investigation, CLI, API, and optional browser tests. |

Inspect the snapshot's event links directly with the embedded Relate API.

```sh
python - <<'PY'
import relate

with relate.connect("examples/synthetic-demo.rl", read_only=True) as graph:
    print(graph.execute("""
        MATCH (parent:Interaction)-[:TRIGGERS]->(child:Interaction)
        RETURN parent.id AS parent_id, child.id AS child_id
        ORDER BY parent_id, child_id
    """).data())
PY
```
